# Ledger API

A double-entry ledger: money is held in accounts and moves only through balanced, immutable
transactions. Transactions are recorded through a REST API and from `payment-settled` Kafka messages,
and every recorded transaction is announced on Kafka. It runs as several instances and keeps every
balance exact under retries, redeliveries and concurrent requests.

## Technologies

| | |
|---|---|
| Language, framework | Java 17, Spring Boot 4.1 (Web MVC, Validation, Actuator) |
| Persistence | MySQL 8.4, Spring Data JDBC + `JdbcClient`, Flyway migrations |
| Messaging | Kafka 4.1 (KRaft, single node), Spring for Apache Kafka |
| API | OpenAPI 3 contract ([`api/openapi.yaml`](api/openapi.yaml)); controllers implement interfaces generated by `openapi-generator` |
| Mapping, boilerplate | MapStruct, Lombok |
| Build, tests | Maven (wrapper), JUnit 5, Testcontainers (real MySQL and Kafka) |
| Runtime | Docker Compose: MySQL, Kafka, two service instances, nginx gateway, Kafka UI |

## Running it

You need Docker, Git and a JDK 17. Maven comes through the wrapper.

```bash
./run.sh
```

It builds the service, runs all the tests (`./mvnw verify`), then starts the whole stack with
`docker compose up --wait`.

| What | Where |
|---|---|
| API, load-balanced over both instances | http://localhost:8080 (another port: `LEDGER_PORT=8090 ./run.sh`) |
| Instance 1 / instance 2 directly | http://localhost:8081, http://localhost:8082 |
| Kafka UI | http://localhost:8085 |

* Stop: `docker compose down -v`
* Tests only: `./mvnw verify` (unit tests only: `./mvnw test`)
* Send a payment-settled message: `./scripts/send-payment.sh <merchantAccountId> 125.50 EUR`
* Watch the announcements: `./scripts/watch-transactions.sh` (dead letters: `--dlt`)

Every `POST` needs an `Idempotency-Key` header (a new UUID per request).

## Architecture

```
                 HTTP                                   Kafka
 client ──► nginx gateway ──► ledger-1 / ledger-2 ◄── payments.settled
                                   │        │
                                   ▼        └────────► ledger.transactions
                                 MySQL                 (via the outbox)
```

Both instances are stateless; everything that must be consistent (balances, locks, idempotency keys,
the outbox) lives in MySQL, so any instance can serve any request.

### Synchronous: the REST API

| | |
|---|---|
| `POST /v1/accounts` | open an account |
| `GET /v1/accounts/{id}` | an account and its balance |
| `GET /v1/accounts/{id}/entries` | its entries, newest first, paged |
| `GET /v1/accounts/{id}/balance?asOf=` | its balance now or at a past instant |
| `POST /v1/transactions` | record a transaction |
| `GET /v1/transactions/{id}` | a transaction and its entries |
| `POST /v1/transactions/{id}/reversal` | reverse a transaction |

Recording a transaction (`controller → IdempotencyService → LedgerService`) runs in **one database
transaction**:

1. **Claim the idempotency key.** A retry with the same key gets the stored response back
   (`Idempotent-Replayed: true`) and nothing happens twice; the same key with a different request is refused.
2. **Lock** every account involved (`SELECT … FOR UPDATE`), one at a time in ascending id order, so
   concurrent transactions can't lose updates or deadlock.
3. **Apply the rules** (`PostingService`): balanced debits and credits, one currency, valid amounts, no
   account past its overdraft limit. A refusal writes nothing.
4. **Write** the transaction, its entries, the new balances, the stored response and an outbox event.

Amounts are decimal strings in the API and `BIGINT` minor units in the database; there is no floating
point anywhere. Errors are RFC 9457 `application/problem+json` with a stable `code`.

### Asynchronous: Kafka

* **In: `payments.settled`.** `PaymentSettledListener` records each settled payment (debit the settlement
  account, credit the merchant) through the same `LedgerService`. It's recorded at most once per payment
  id, however often it's redelivered. Messages that can't be recorded go to `payments.settled.DLT`.
  The offset is committed only after the database commit, so a crash means redelivery, never loss.
* **Out: `ledger.transactions`.** Every recorded transaction gets an event in the `outbox_events` table,
  in the same database transaction. `OutboxRelay` publishes the table to Kafka in order (one instance
  at a time) and marks rows as published. Events are keyed by currency, so all transactions on an
  account arrive in the order they were applied. Delivery is at-least-once: consumers deduplicate on the
  transaction id.
